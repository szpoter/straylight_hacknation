# 11 · REST API dla zwykłego czatu, pliku jurora i pamięci rodziny

**Rezultat dla jurora.** Ten sam klient HTTP może założyć sesję, otworzyć sprawę, przekazać potwierdzone fakty, uzyskać ocenę, wskazać korektę i odtworzyć źródła po odświeżeniu. Przeglądarka dodaje lokalny odczyt PDF. Konsument API może wykonać ten przebieg na strukturalnych danych bez klikania w UI. Projekt v1 obejmuje 13 ścieżek i 20 operacji. Ich typy, wymagane nagłówki, statusy i formaty danych zawiera [specyfikacja OpenAPI 3.1.1](api-v1.openapi.yaml).

Rozdział 5 briefu ZUS zaleca REST API do integracji backendu z warstwą prezentacji. W tym projekcie przyjmujemy je jako warunek odbioru zwykłego czatu. Dane konta ZUS nadal pochodzą z symulacji przewidzianej w zadaniu. [Brief ZUS, rozdziały 3 i 5](<../../Materiały hackathonowe/ZUS - Pełna treść zadania konkursowego.pdf>)

## Punkt wyjścia i migracja istniejących klientów

Dzisiaj aplikacja ma dziewięć plików route.ts i 12 operacji HTTP pod ścieżkami domenowymi. Wykorzystać istniejące moduły sesji, repozytoria Postgresa, walidację i reguły. V1 dostaje cienkie handlery Next.js w app/src/app/api/v1. Warstwa domenowa powinna być wywoływana wprost przez stare i nowe handlery. [Obecne endpointy](../../app/src/app/api) · [Serwis pytań](../../app/src/lib/zusik/ask-service.ts) · [Sesja](../../app/src/lib/zusik/session.ts)

| Obecny punkt wejścia | Co robić podczas migracji |
|---|---|
| POST /api/zusik/session, GET /api/zusik/state | Zachować podpis istniejącego cookie i odczyt starych sesji. V1 rozpoczyna się od POST /sessions. Do wznowienia używać list spraw/profili i odczytu konkretnego zasobu. Stary ekran nadal dostaje dotychczasowy kształt stanu. |
| POST /api/zusik/ask | Wydzielić wspólną obsługę pytań publicznych. Stary klient zachowuje requestId, JSON oraz application/x-ndjson i dotychczasowe ramki aktywności, delty i wyniku. V1 ma zasób wiadomości odczytywany przez GET. Oba adaptery muszą wskazywać tę samą operację przy ponowieniu przez tego samego klienta. [Czytnik strumienia](../../app/src/lib/zusik/ask-stream.ts) |
| GET i POST /api/zusik/marta, GET /api/zusik/marta/pdf | Zachować odczyt starych szkiców i PDF. Przenosić zdarzenia wniosku do modelu sprawy dopiero po mapowaniu właściciela i ID. Każde mapowanie starego rekordu jest powtarzalne. |
| GET i POST /api/zusik/sickness, GET /api/zusik/sickness/evidence/{id}, GET i POST /api/kamil | Zachować dedykowane wejścia i ich kontrolę właściciela. Z v1 współdzielić walidowane fakty, reguły i dowody po testach zgodności dla danej ścieżki. |
| POST /api/zusik | Pozostawić jako dotychczasową sondę. Uprawnienia operatora indeksu oraz klucz zapisu Qdrant są poza API jurora. |

## Zasoby i kolejność budowy

Wszystkie skrócone adresy w kolejnych sekcjach mają prefiks /api/v1. Aktualna wersja opisana w YAML jest projektem. Pierwszą wdrażaną pionową ścieżką jest sesja → profil → fakt → sprawa → pytanie → odpowiedź po odświeżeniu.

| Właściciel i zasób | Operacje | Niezmiennik domenowy przy odbiorze |
|---|---|---|
| D · sesja | POST /sessions | Pierwsze wywołanie zakłada sesję demo i ustawia HttpOnly cookie. Kolejne z tym samym ważnym cookie wznawia ten sam zakres. Klient bez cookie zaczyna jako nowy właściciel. |
| B i D · profil | POST, GET /profiles. GET, PATCH, DELETE /profiles/{profileId} | Rodzina planu i profil zaimportowanych akt mają osobne ID. Jedna transakcja PATCH dodaje osoby i fakty lub koryguje wskazaną wersję. Zwrócić rewizję oraz silny ETag. |
| B · pamięć | GET /profiles/{profileId}/facts i /proposals | Fakty można filtrować po osobie, dniu obowiązywania validAt i chwili wiedzy knownAt. Obie granice można stosować naraz. Propozycja może zostać zaakceptowana albo odrzucona przez PATCH profilu. |
| D · sprawa | POST, GET /cases. GET, DELETE /cases/{caseId} | Podany profileId musi być dostępny dla tej samej sesji. Przeładowanie aplikacji wznawia konkretny caseId. Dla nowego pliku z innej rodziny utworzyć osobny profil importu. |
| A i D · dokument | POST, GET /cases/{caseId}/documents. GET zasobu po documentId | Rejestrujemy typ, liczbę stron i niejawny dla innych spraw clientDocumentId. Obraz, nazwisko w nazwie pliku i pełny OCR pozostają u jurora. Powtórzony import tego samego lokalnego dokumentu w tej sprawie wskazuje ten sam rekord. |
| D · wiadomość | POST, GET /cases/{caseId}/messages. GET zasobu po messageId | Wspólny kod obsługuje wolne pytanie publiczne, odczyt faktu, deklarację, pytanie o sprawę, wyjaśnienie i hipotezę. W historii jest jedna wiadomość logiczna po ponowieniu i jednoznaczne źródła wyniku. |
| C i D · ocena | POST /cases/{caseId}/assessments. GET zasobu po assessmentId | Przekazać rewizje sprawy i profilu, osobę, datę i świadczenie. Serwer wybiera wersję reguły i dowody. Zwrócić decyzje dla okresów z oddzielnym statusem wyliczenia, groszami przy wyliczonej kwocie oraz źródłem. Stary wynik pozostaje odtwarzalny i zyskuje stale po zmianie wejścia. |

**Sposób obsługi wolnego tekstu.** UI przyjmuje normalną wypowiedź. Lokalny router wyodrębnia pytanie publiczne lub minimalny prywatny zestaw pól przewidziany w MessageInput. Serwer powtarza walidację. Przy niejednoznacznej osobie, dacie lub intencji zadać jedno pytanie w tej samej rozmowie. O pytanie ogólne można zapytać bez dokumentu i bez uzupełnienia danych rodziny. Utworzenie pustego profilu i sprawy technicznej wykonuje klient raz przy pierwszym wysłaniu. Rozbudowane prywatne pytanie można obsłużyć lokalnie lub podzielić na publiczny temat i prywatny odczyt. Podczas hipotezy rozliczać wariant wyłącznie w obrębie symulacji. Klient nie musi znać promptów ani dostawcy modelu. [Routing i pamięć](10-pamiec-uzytkownika-i-kontekst.md)

## Umowa HTTP i bezpieczeństwo danych

- **Tożsamość.** Serwer ustala właściciela z podpisanego cookie. Obecna sesja demo trwa siedem dni. Klient integracyjny zachowuje cookie w prywatnym cookie jar. Produkcyjny dostęp między urządzeniami lub dla partnera wymaga jawnej tożsamości, osobno wydanych uprawnień i testu odzyskania/odwołania. Nie wystawiać wspólnego klucza właściciela wielu rodzin w JS. Dla zapisu przeglądarkowego stosować kontrolę Origin wobec skonfigurowanego pochodzenia, HTTPS i HttpOnly/SameSite. Politykę klienta bez Origin określić przy wdrożeniu i sprawdzić testem; najprostszy klient demo wysyła właściwy Origin. Identyfikatory właściciela z body są niedozwolone.
- **Uprawnienia i przechowywanie.** Wszystkie zapytania i złączenia obejmują właściciela, profil oraz sprawę. Tak samo w tle, przy pobieraniu dowodu i odtwarzaniu wyniku po kluczu. Cudza sprawa lub dowód daje takie samo 404 jak nieistniejący. Użyć bieżącego Postgresa i migracji addytywnej z kluczami obcymi. Jeżeli nowe tabele są udostępniane przez Supabase, włączyć RLS osobno dla każdej operacji i roli z rzeczywistym auth.uid(); cookie demonstracyjne samo nie ustanawia tożsamości Supabase. Prywatne odpowiedzi wysyłać z Cache-Control: private, no-store. Użytkownik widzi źródło i może usunąć zakres. [HTTP caching](https://www.rfc-editor.org/rfc/rfc9111.html)
- **Typy i dowody.** JSON walidować dotychczasowym Zod na granicy serwera. Dni w formacie YYYY-MM-DD, chwile z jawną strefą, kwoty całkowite w groszach PLN, identyfikatory nieprzenoszące danych osobowych. Sprawdzać zakres dat, liczbę stron, indeks strony od 1, walutę i rodzaj wartości dla danego pola oraz związek płatnika z tytułem. Oba krańce okresu świadczenia i obowiązywania faktu w API są włączne, zgodnie z aktami i plikiem 03. Dla nierozpoznanej daty przechować kandydaturę lokalnie do doprecyzowania. Serwer ustala wiarygodność źródła z jego rejestru. Pole „simulated_zus” przesłane przez rodzica nie nadaje deklaracji uprawnień urzędu. Powiązania dowodów sprawdzić przed transakcją. Dla publicznych cytatów zwracać ID fragmentu i wersję rozwiązywane do istniejącego adresu źródłowego, dla prywatnych tylko autoryzowany lokalizator. Pierwszy zakres pól w YAML rozszerzać według potrzeb kolejnych rodzin z akt.
- **Równoczesne zmiany.** GET zasobu zwraca silny ETag. Przy PATCH/DELETE wymagać dokładnego If-Match. Jego brak daje 428, nieaktualny daje 412. PATCH wykonuje wszystkie zmiany atomowo; błąd ostatniej cofa wcześniejsze w tej paczce. Przy ocenie POST porównać także wskazane rewizje obu zasobów, rozbieżność daje 409. Klient po konflikcie odczytuje aktualny stan i pokazuje różnicę. [Semantyka HTTP](https://www.rfc-editor.org/rfc/rfc9110.html) · [Precondition Required](https://www.rfc-editor.org/rfc/rfc6585.html)
- **Ponowienia.** POST tworzący zasób i PATCH wymagają Idempotency-Key. Unikat obejmuje właściciela, metodę, zasób i klucz. Zapisać skrót kanonicznego body oraz istotnych warunków żądania, status, Location i ID wyniku w tej samej transakcji co efekt. Po autoryzacji identyczne ponowienie zwraca utrwalony wynik przed ponowną kontrolą starego ETag. Zmienione żądanie z tym samym kluczem daje 409. Wydzielić bezpieczne wznowienie zablokowanej operacji i termin retencji wpisu co najmniej tak długi jak obsługiwane okno ponowień klienta. Usunięcie danych wyklucza odtworzenie ich ciała z cache klucza. Drugi DELETE usuniętego zasobu może dać 404. Dla tego API klucz jest jawnie zdefiniowaną konwencją projektu.
- **Długa odpowiedź.** Pierwszy etap może zwracać 201 i gotową wiadomość. Dopiero przy istniejącym trwałym wykonawcy użyć 202 z Location wiadomości i Retry-After. Przed odpowiedzią 202 utrwalić zadanie ze stanem processing. Worker atomowo przejmuje pracę, zapisuje completed/failed i wynik tylko raz. GET pozwala kontynuować po F5. Błąd już przyjętego zadania ma stabilny errorCode. Awaria przy przyjmowaniu bez zapisu daje 503. Żadne odpytywanie GET nie uruchamia nowej oceny. [Projektowanie zasobów i operacji asynchronicznych](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design)
- **Odpowiedzi, listy i limity.** Utworzenie zwraca 201 i Location. Pomyślne usunięcie zwraca 204 bez ciała. Błędny JSON daje 400, brak ważnej sesji 401, niedozwolone pochodzenie 403, zbyt duża treść 413, niewłaściwy Content-Type 415, niespójne dane dziedzinowe 422, a przekroczenie limitu 429 z Retry-After. Błędy aplikacji zwracają application/problem+json z polami type, title, status, code i requestId. Nie kopiować prywatnej wartości do komunikatu. Listy mają domyślnie 25, maksymalnie 100 wpisów oraz nieprzezroczysty kursor powiązany z właścicielem, filtrami i stabilnym porządkiem (czas, ID). Ograniczyć rozmiar requestu przed dekodowaniem. [Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html) · [Opis kontraktu OpenAPI](https://spec.openapis.org/oas/v3.1.1.html)

## Jedna próba z konkretnymi danymi

Przykład używa wyłącznie identyfikatorów syntetycznych. Klient zachowuje cookie i wysyła Content-Type: application/json, ten sam Origin co aplikacja i nowy klucz dla każdej nowej mutacji wymagającej klucza. Poniższe ID zasobów należy w próbie zastąpić tymi zwróconymi przez serwer.

1. POST /sessions → 200. POST /profiles z {"mode":"case_import"} → 201, Location i ETag. GET pod Location → ten sam profil i walidator. POST /cases z {"profileId":"P"} → 201 z ID sprawy C.
2. PATCH /profiles/P z If-Match otrzymanym z GET i jednym Idempotency-Key. Poniższa paczka tworzy osobę i jeden fakt. W przykładzie referencja ma typ lokalnej deklaracji i jest rejestrowana w obrębie tej operacji. Ponowienie dokładnie tej paczki z tym samym kluczem zwraca ten sam rezultat.

```json
{"changes":[
  {"action":"add_subject","subjectId":"osoba-A","role":"parent"},
  {"action":"add_fact","fact":{"subjectId":"osoba-A","field":"monthlyGrossPay",
   "value":{"kind":"money","grosze":600000,"currency":"PLN"},
   "validFrom":"2026-02-01","validTo":"2026-02-28","payerRef":"platnik-P",
   "source":{"kind":"declaration","referenceId":"deklaracja-A"}}}
]}
```

3. POST /cases/C/messages z {"intent":"read_context","topic":"monthlyGrossPay","subjectId":"osoba-A","validAt":"2026-02-15"}. Oczekiwane 201 lub 202 i późniejsze GET. Odpowiedź podaje 6000 zł brutto za luty jako deklarację i wskazuje jej wersję. Zwykłe pytanie publiczne w tej sprawie może mieć {"intent":"public_question","publicQuestion":"Komu ZUS wypłaca świadczenie aktywnie w żłobku?"}. Ono wymaga źródła urzędowego.
4. Po dodaniu zaświadczenia przez POST /cases/C/documents pobrać ID dowodu. Zarejestrować proponowaną wypłatę 650000 groszy z numerem strony w tej samej sprawie. Po wyjaśnieniu konfliktu przyjąć propozycję lub użyć correct_fact z ID poprzedniego faktu. Druga karta z dawnym ETag i nowym kluczem ma dostać 412. GET /profiles/P/facts?validAt=2026-02-15 z dawnym knownAt pozwala odtworzyć pierwszą odpowiedź, a bez tego ograniczenia odczytać aktualny stan. Kwoty z przykładu opisują wynagrodzenie.
5. POST /cases/C/assessments z {"subjectId":"osoba-A","asOf":"2026-02-15","caseRevision":1,"profileRevision":2,"benefit":"maternity"} z rewizjami właśnie odczytanymi z GET. Pojedyncze wynagrodzenie nie ustala prawa ani pełnej podstawy. Odpowiedź ma ujawnić konkretne braki i status kwoty. Po dostarczeniu pełnego syntetycznego zestawu uruchomić nową ocenę, sprawdzić kwotę z kalkulatorem i źródła, po czym odczytać obie oceny przez osobne ID. Dla innego cookie oba odczyty dają 404.
6. W nowej karcie wznowić C i historię wiadomości. Usunąć najpierw C z właściwym If-Match, potem P. Usunięcie sprawy usuwa jej wiadomości, dokumenty, propozycje z tych dowodów i oceny. Unieważnić fakty zależne wyłącznie od tych dokumentów. Usunięcie profilu usuwa wszystkie jego zależności. Przetestować równoczesny worker oraz stary klucz ponowienia po usunięciu.

**Warunek wydania.** Test kontraktowy obejmuje każdą z 20 operacji, uprawnienia do obiektów podrzędnych, pomyślne oraz błędne warunki zapisu. Co najmniej jedna automatyczna próba prowadzi od tekstu rodzica w przeglądarce przez rzeczywiste API i bazę aż do odpowiedzi po korekcie. Logi operatora zawierają identyfikator żądania, nazwę operacji, czas, status i wersje, bez prywatnego pytania, identyfikatorów urzędowych i tekstu akt. Raport jawnie wskazuje etap dostępny na Preview i operacje, które pozostały w projekcie.
